1. L'Ecosistema de Paquets: Pub.dev

El SDK de Flutter inclou els ginys bàsics del sistema de disseny Material i Cupertino vist al Tema 2. Tanmateix, Flutter compta amb un repositori oficial de paquets creats per la comunitat i l'equip de Google: Pub.dev.

🔍 Com analitzar i seleccionar un paquet a Pub.dev:

Abans d'afegir qualsevol llibreria al projecte, cal revisar les mètriques de la fitxa del paquet:

  • Likes: Nombre de desenvolupadors que han votat positivament el paquet.
  • Pub Points (Màxim 140): Avaluació automàtica de qualitat basada en format de codi, documentació, tests i compatibilitat amb el Null Safety.
  • Popularity: Percentatge d'ús del paquet en comparació amb la resta del repositori.
  • Pestanya Installing i Example: Proporciona el comando d'instal·lació i snippets de codi funcionals.

Instal·lació de dependències a `pubspec.yaml`

Pots afegir paquets executant el comando des de la terminal integrada de VS Code o Android Studio:

flutter pub add url_launcher
flutter pub add http

Aquesta acció modifica automàticament el fitxer pubspec.yaml del projecte:

dependencies:
  flutter:
    sdk: flutter
  http: ^1.2.0
  url_launcher: ^6.2.4

2. Paquets Comunitaris Essencials (Exemples Pràctics)

2.1 Navegació externa i accions de sistema: url_launcher

Permet obrir adreces web externes al navegador per defecte del dispositiu, realitzar trucades de telèfon (tel:) o obrir l'aplicació de correu (mailto:).

import 'package:flutter/material.dart';
import 'package:url_launcher/url_launcher.dart';

class UrlLauncherExample extends StatelessWidget {
  const UrlLauncherExample({super.key});

  Future<void> _obrirWeb(String urlString) async {
    final Uri url = Uri.parse(urlString);
    if (!await launchUrl(url, mode: LaunchMode.externalApplication)) {
      throw Exception('No s\'ha pogut obrir la URL: $urlString');
    }
  }

  @override
  Widget build(BuildContext context) {
    return ElevatedButton.icon(
      onPressed: () => _obrirWeb('https://jaumecf.github.io/PMM/'),
      icon: const Icon(Icons.open_in_browser),
      label: const Text('Obrir Web PMM'),
    );
  }
}

2.2 Petició HTTP i Consum d'APIs REST: http

El paquet http facilita la realització de peticions asíncrones (GET, POST, PUT, DELETE) contra un servidor o API REST externa.

import 'dart:convert';
import 'package:flutter/material.dart';
import 'package:http/http.dart' as http;

class HttpExampleWidget extends StatefulWidget {
  const HttpExampleWidget({super.key});

  @override
  State<HttpExampleWidget> createState() => _HttpExampleWidgetState();
}

class _HttpExampleWidgetState extends State<HttpExampleWidget> {
  String _titolPost = 'Carregant...';

  @override
  void initState() {
    super.initState();
    _carregarDades();
  }

  Future<void> _carregarDades() async {
    final response = await http.get(
      Uri.parse('https://jsonplaceholder.typicode.com/posts/1'),
    );

    if (response.statusCode == 200) {
      final data = jsonDecode(response.body);
      setState(() {
        _titolPost = data['title'];
      });
    }
  }

  @override
  Widget build(BuildContext context) {
    return Card(
      child: Padding(
        padding: const EdgeInsets.all(12.0),
        child: Text('Post 1: $_titolPost'),
      ),
    );
  }
}

3. El Repte de la Gestió d'Estat (State Management)

A mesura que l'aplicació creix i té múltiples pantalles, gestionar les dades només amb el mètode setState() vist al Tema 2 esdevé ineficient per dos motius principals:

⚠️ Ephemeral State vs App State:
  • Estat Efímer (Ephemeral State): Estat local d'un sol widget (ex. la pestanya seleccionada a un BottomNavigationBar o el text temporal d'un camp de formulari). Es gestiona perfectament amb StatefulWidget i setState().
  • Estat de l'Aplicació (App State): Dades globals compartides per múltiples pantalles o widgets distants (ex. la sessió de l'usuari autenticat, la cistella de la compra o les preferències del tema).

Quan s'intenta passar dades globals mitjançant constructors de widgets nocius, es produeix el fenomen anomenat Prop Drilling (passar paràmetres a través de 5 o 6 widgets intermedis que no necessiten aquesta informació). Per evitar-ho, utilitzem patrons de gestió d'estat globals.

4. Provider: La Solució Oficial Recomanada

provider és la llibreria oficial recomanada per l'equip de desenvolupament de Flutter. Utilitza la injecció de dependències per posar un objecte a disposició de qualsevol widget inferior de l'arbre.

1. Definir el Model d'Estat (`ChangeNotifier`)

import 'package:flutter/material.dart';

class ContadorModel extends ChangeNotifier {
  int _valor = 0;

  int get valor => _valor;

  void incrementar() {
    _valor++;
    notifyListeners(); // Notifica als widgets escoltadors que s'han de redibuixar
  }
}

2. Injectar el Provider a l'Arrel (`ChangeNotifierProvider`)

import 'package:flutter/material.dart';
import 'package:provider/provider.dart';

void main() {
  runApp(
    ChangeNotifierProvider(
      create: (context) => ContadorModel(),
      child: const MyApp(),
    ),
  );
}

3. Consumir l'Estat (`context.watch` i `context.read`)

class PantallaContadorProvider extends StatelessWidget {
  const PantallaContadorProvider({super.key});

  @override
  Widget build(BuildContext context) {
    // context.watch re-executa el mètode build() quan l'estat canvia
    final contador = context.watch<ContadorModel>();

    return Scaffold(
      appBar: AppBar(title: const Text('Provider Demo')),
      body: Center(
        child: Text('Valor actual: ${contador.valor}', style: const TextStyle(fontSize: 22)),
      ),
      floatingActionButton: FloatingActionButton(
        // context.read s'utilitza en callbacks sense escoltar canvis de re-dibuix
        onPressed: () => context.read<ContadorModel>().incrementar(),
        child: const Icon(Icons.add),
      ),
    );
  }
}

5. Riverpod: L'Evolució Moderna de Provider

Riverpod és un re-disseny complet de Provider creat pel mateix autor (Remi Rousselet). Resol les restriccions històriques de dependre del BuildContext, evita errors d'injecció en temps d'execució i és completament segur en temps de compilació.

🚀 Avantatges clau de Riverpod sobre Provider:
  • Fora de l'arbre de widgets (No-BuildContext): Els providers es declaren com a constants globals i es poden accedir des de qualsevol lloc.
  • Seguretat en temps de compilació: És impossible obtenir un ProviderNotFoundException en temps d'execució.
  • Fàcil de testejar: Permet sobreescriure (override) l'estat de qualsevol provider fàcilment en tests unitaris.

1. Definir la lògica amb `Notifier` i `NotifierProvider`

import 'package:flutter_riverpod/flutter_riverpod.dart';

// 1. Classe Notifier amb la lògica de negoci
class ContadorNotifier extends Notifier<int> {
  @override
  int build() {
    return 0; // Estat inicial
  }

  void incrementar() {
    state++; // Modificació d'estat reactiu
  }
}

// 2. Provider Global de Riverpod
final contadorProvider = NotifierProvider<ContadorNotifier, int>(() {
  return ContadorNotifier();
});

2. Embolcallar l'aplicació amb `ProviderScope`

import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

void main() {
  runApp(
    // ProviderScope manté l'estat de tots els providers de Riverpod
    const ProviderScope(
      child: MyAppRiverpod(),
    ),
  );
}

3. Consumir l'estat amb `ConsumerWidget` i `WidgetRef`

// Subtituïm StatelessWidget per ConsumerWidget
class PantallaContadorRiverpod extends ConsumerWidget {
  const PantallaContadorRiverpod({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    // ref.watch escolta el provider i redibuixa la interfície quan canvia
    final valorContador = ref.watch(contadorProvider);

    return Scaffold(
      appBar: AppBar(title: const Text('Riverpod Demo')),
      body: Center(
        child: Text('Valor actual: $valorContador', style: const TextStyle(fontSize: 22)),
      ),
      floatingActionButton: FloatingActionButton(
        // ref.read s'usa en esdeveniments per executar funcions del notifier
        onPressed: () => ref.read(contadorProvider.notifier).incrementar(),
        child: const Icon(Icons.add),
      ),
    );
  }
}

En utilitzar Riverpod per a la gestió d'estat complexa, hem de triar la classe base adequada segons si la lògica és síncrona o asíncrona i si necessita rebre paràmetres (.family) des de la interfície.

Classe Base És Asíncron? (API/DB) Rep Paràmetres? (.family) Estat gestionat Exemple d'ús típic
Notifier<T> ❌ No (Síncron) ❌ No T Comptador simple, selector de tema.
FamilyNotifier<T, Arg> ❌ No (Síncron) ✅ Sí T Comptador o estat associat a un ID concret.
AsyncNotifier<T> ✅ Sí (Asíncron) ❌ No AsyncValue<T> Carregar el perfil de l'usuari actual connectat.
FamilyAsyncNotifier<T, Arg> ✅ Sí (Asíncron) ✅ Sí AsyncValue<T> Carregar un detall d'element per ID (/users/:id).
💡 Quin triar a la pràctica?
  • Si les dades venen d'un Future (API REST o SQLite) 👉 Utilitza AsyncNotifier o FamilyAsyncNotifier. Això et permetrà utilitzar state.when(...) a la UI per gestionar la càrrega i els errors automàticament.
  • Si l'estat és purament en memòria i no fa peticions asíncrones 👉 Utilitza Notifier o FamilyNotifier.
