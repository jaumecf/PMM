Tema 4: Persistència de Dades i Serveis al Núvol

Emmagatzematge local (SharedPreferences, SQLite), arquitectura reactiva amb Provider i ecosistema Firebase

1. Fonaments de la Persistència en Dispositius Mòbils

Fins ara, totes les dades gestionades dins dels nostres widgets o gestors d'estat residien a la memòria RAM (memòria volàtil). Quan l'usuari tanca l'aplicació o el sistema operatiu l'elimina per alliberar recursos, tota aquesta informació es perd.

📂 El Sistema de Fitxers i Sandbox:

Per seguretat, tant Android com iOS aïllen cada aplicació dins d'un entorn tancat (Sandbox). Una app no pot accedir directament als fitxers d'una altra. Per obtenir les rutes del sistema de manera multiplataforma utilitzem el paquet oficial path_provider:

  • Temporary Directory (getTemporaryDirectory()): Emmagatzematge de memòria cau (caché) que el sistema operatiu pot esborrar automàticament si es queda sense espai.
  • Application Documents Directory (getApplicationDocumentsDirectory()): Directori persistent per a dades generades per l'usuari que només s'esborren si es desinstal·la l'aplicació.

1.1 Serialització i Deserialització de Models

Per desar un objecte de Dart en una base de dades local, un fitxer JSON o enviar-lo al núvol, cal convertir-lo a un format primitiu (Map<String, dynamic> o String). Aquest procés s'anomena serialització:

class Tasca {
  final int? id;
  final String titol;
  final bool completada;

  Tasca({this.id, required this.titol, this.completada = false});

  // 1. Serialització: Objecte Dart -> Map (per a SQLite, Firestore o JSON)
  Map<String, dynamic> toMap() {
    return {
      if (id != null) 'id': id,
      'titol': titol,
      // SQLite no té tipus boolean natiu: guardem 1 (true) o 0 (false)
      'completada': completada ? 1 : 0,
    };
  }

  // 2. Deserialització: Map -> Objecte Dart
  factory Tasca.fromMap(Map<String, dynamic> map) {
    return Tasca(
      id: map['id'] as int?,
      titol: map['titol'] as String,
      completada: (map['completada'] == 1 || map['completada'] == true),
    );
  }
}

2. Persistència Lleugera Clau-Valor: shared_preferences

El paquet shared_preferences embolcalla SharedPreferences a Android i NSUserDefaults a iOS. Està dissenyat per desar petits conjunts de dades primitives (int, double, bool, String i List<String>).

🔐 Seguretat — Què NO s'ha de guardar mai a SharedPreferences?

SharedPreferences desa un fitxer XML/PLIST sense xifrar al dispositiu. Mai s'hi han d'emmagatzemar contrasenyes, tokens JWT de sessió o claus API. Per a dades sensibles cal utilitzar flutter_secure_storage (que utilitza Keystore a Android i Keychain a iOS).

2.1 Integració Reactiva amb Provider (ChangeNotifier)

Un patró molt habitual en aplicacions reals és combinar SharedPreferences amb un ChangeNotifier de Provider per persistir la configuració de l'usuari (per exemple, el tema fosc) i actualitzar tota la interfície automàticament:

1. Instal·lació i Model d'Estat Persistent

flutter pub add shared_preferences provider
import 'package:flutter/material.dart';
import 'package:shared_preferences/shared_preferences.dart';

class PreferenciesProvider extends ChangeNotifier {
  static const String _clauTemaFosc = 'es_tema_fosc';
  bool _esTemaFosc = false;

  bool get esTemaFosc => _esTemaFosc;

  PreferenciesProvider() {
    _carregarPreferencies();
  }

  // Llegeix del disc en arrencar l'aplicació
  Future<void> _carregarPreferencies() async {
    final prefs = await SharedPreferences.getInstance();
    _esTemaFosc = prefs.getBool(_clauTemaFosc) ?? false;
    notifyListeners();
  }

  // Desa al disc i notifica a la UI
  Future<void> canviarTema(bool nouValor) async {
    _esTemaFosc = nouValor;
    notifyListeners(); // Resposta immediata a la UI

    final prefs = await SharedPreferences.getInstance();
    await prefs.setBool(_clauTemaFosc, nouValor);
  }
}

Quan necessitem emmagatzemar milers de registres estructurats, fer cerques complexes, ordenacions o establir relacions entre taules (claus foranes), utilitzem SQLite mitjançant el paquet sqflite.

flutter pub add sqflite path

3.1 Patró Singleton i Gestió d'Esquema (DatabaseHelper)

Obrir una connexió a la base de dades és una operació costosa. Per evitar bloquejos o corrupció de dades, s'aplica el patró Singleton per garantir una única instància de Database en tota l'aplicació:

import 'package:path/path.dart';
import 'package:sqflite/sqflite.dart';
import 'tasca_model.dart';

class DatabaseHelper {
  // Instància única (Singleton)
  static final DatabaseHelper instance = DatabaseHelper._init();
  static Database? _database;

  DatabaseHelper._init();

  Future<Database> get database async {
    if (_database != null) return _database!;
    _database = await _initDB('tasques_app.db');
    return _database!;
  }

  Future<Database> _initDB(String filePath) async {
    final dbPath = await getDatabasesPath();
    final path = join(dbPath, filePath);

    return await openDatabase(
      path,
      version: 1,
      onCreate: _createDB,
      onUpgrade: _upgradeDB,
    );
  }

  // S'executa només la primera vegada que es crea la BD
  Future<void> _createDB(Database db, int version) async {
    await db.execute('''
      CREATE TABLE tasques (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        titol TEXT NOT NULL,
        completada INTEGER NOT NULL
      )
    ''');
  }

  // S'executa quan incrementem el número de 'version'
  Future<void> _upgradeDB(Database db, int oldVersion, int newVersion) async {
    if (oldVersion < 2) {
      await db.execute('ALTER TABLE tasques ADD COLUMN prioritat INTEGER DEFAULT 1');
    }
  }

  // --- OPERACIONS CRUD SEGURES (Parametritzades) ---

  Future<int> crearTasca(Tasca tasca) async {
    final db = await instance.database;
    return await db.insert('tasques', tasca.toMap());
  }

  Future<List<Tasca>> obtenirTotesLesTasques() async {
    final db = await instance.database;
    final resultat = await db.query('tasques', orderBy: 'id DESC');
    return resultat.map((json) => Tasca.fromMap(json)).toList();
  }

  Future<int> actualitzarTasca(Tasca tasca) async {
    final db = await instance.database;
    return await db.update(
      'tasques',
      tasca.toMap(),
      where: 'id = ?', // Prevenció d'SQL Injection
      whereArgs: [tasca.id],
    );
  }

  Future<int> eliminarTasca(int id) async {
    final db = await instance.database;
    return await db.delete(
      'tasques',
      where: 'id = ?',
      whereArgs: [id],
    );
  }
}

3.2 Desacoblament UI — SQLite amb Provider

Els widgets mai han de contenir sentències SQL. Creem un TasquesProvider que actua d'intermediari entre la base de dades i la interfície:

import 'package:flutter/material.dart';
import 'database_helper.dart';
import 'tasca_model.dart';

class TasquesProvider extends ChangeNotifier {
  List<Tasca> _tasques = [];
  bool _carregant = false;

  List<Tasca> get tasques => _tasques;
  bool get carregant => _carregant;

  Future<void> carregarTasques() async {
    _carregant = true;
    notifyListeners();

    _tasques = await DatabaseHelper.instance.obtenirTotesLesTasques();

    _carregant = false;
    notifyListeners();
  }

  Future<void> afegirTasca(String titol) async {
    final novaTasca = Tasca(titol: titol);
    await DatabaseHelper.instance.crearTasca(novaTasca);
    await carregarTasques(); // Refresca la llista des de SQLite
  }

  Future<void> esborrarTasca(int id) async {
    await DatabaseHelper.instance.eliminarTasca(id);
    _tasques.removeWhere((t) => t.id == id);
    notifyListeners();
  }
}

4. Bases de Dades NoSQL i ORMs Moderns en Local

Escriure SQL manualment amb sqflite és potent però propens a errors de tipat en temps d'execució. L'ecosistema Flutter disposa d'alternatives modernes segons les necessitats del projecte:

Tecnologia Tipus Avantatge Principal Cas d'ús ideal
sqflite SQL Relacional Control total sobre SQL, estàndard consolidat i zero màgia oculta. Aplicacions amb consultes SQL complexes, JOINs o migracions manuals.
Drift (abans Moor) ORM Reactiu sobre SQLite Consultes verificades en temps de compilació i suport natiu per a Streams. Projectes mitjans/grans que requereixen seguretat de tipus i reactivitat SQL.
Hive CE / ObjectBox NoSQL / Objectes Velocitat extrema (escrits en Dart/C++ natiu), sense necessitat de SQL. Memòria cau d'objectes, emmagatzematge ràpid de models sense relacions complexes.

5. Persistència al Núvol i BaaS: Firebase

Firebase és la plataforma Backend-as-a-Service (BaaS) de Google. Permet disposar d'autenticació, bases de dades en temps real, emmagatzematge de fitxers i notificacions sense haver de programar ni mantenir un servidor propi.

5.1 Configuració Moderna amb FlutterFire CLI

Actualment no cal copiar manualment fitxers JSON/PLIST per configurar Firebase. S'utilitza l'eina oficial FlutterFire CLI:

5.2 Cloud Firestore vs. Firebase Realtime Database

Firebase ofereix dues bases de dades NoSQL al núvol amb sincronització en temps real i suport offline automàtic, però amb arquitectures molt diferents:

Característica Cloud Firestore (Recomanada) Firebase Realtime Database
Model de Dades Col·leccions i Documents (similars a JSON amb subcol·leccions). Un únic arbre JSON gegant.
Consultes i Filtres Consultes compostes avançades (múltiples where, ordenació i paginació). Consultes limitades (només pots ordenar o filtrar per una propietat alhora).
Escalabilitat Escalabilitat global automàtica. Les consultes escalen segons els resultats, no la mida de la BD. Requereix desnormalitzar molt les dades per evitar descarregar branques senceres.
Model de Facturació Per nombre d'operacions (lectures, escriptures i esborrats). Per ample de banda (GB descarregats) i emmagatzematge.
Quan triar-la? En el 90% dels projectes nous (apps socials, gestors, comerç electrònic). Apps amb moltíssimes escriptures petites i baixa latència (ex. telemetria IoT, presència online).

5.3 Cloud Firestore + StreamProvider (Temps Real)

A Firestore, les dades s'organitzen en Col·leccions (ex: notes) que contenen Documents (cada nota amb el seu id únic i camps). Utilitzant snapshots() obtenim un Stream que emet dades cada vegada que canvia la base de dades al núvol:

Servei Firestore i Consum amb Provider

import 'package:cloud_firestore/cloud_firestore.dart';

class FirestoreService {
  final CollectionReference _notesRef =
      FirebaseFirestore.instance.collection('notes');

  // Escolta en temps real ordenada per data
  Stream<QuerySnapshot> getNotesStream(String uid) {
    return _notesRef
        .where('userId', isEqualTo: uid)
        .orderBy('dataCreacio', descending: true)
        .snapshots();
  }

  // Crear document nou
  Future<void> afegirNota(String titol, String uid) {
    return _notesRef.add({
      'titol': titol,
      'userId': uid,
      'dataCreacio': FieldValue.serverTimestamp(),
    });
  }

  // Eliminar document per ID
  Future<void> eliminarNota(String docId) {
    return _notesRef.doc(docId).delete();
  }
}

5.4 Firebase Authentication (firebase_auth)

Firebase Authentication gestiona tot el cicle d'identitat dels usuaris (registre, inici de sessió, recuperació de contrasenya, tokens JWT i renovació automàtica de sessió) mitjançant correu/contrasenya o proveïdors OAuth (Google, Apple, GitHub).

import 'package:firebase_auth/firebase_auth.dart';
import 'package:flutter/material.dart';

class AuthProvider extends ChangeNotifier {
  final FirebaseAuth _auth = FirebaseAuth.instance;
  User? _usuari;

  User? get usuari => _usuari;
  bool get estaAutenticat => _usuari != null;

  AuthProvider() {
    // Escolta contínuament si l'usuari inicia o tanca sessió
    _auth.authStateChanges().listen((User? user) {
      _usuari = user;
      notifyListeners();
    });
  }

  Future<void> iniciarSessio(String email, String password) async {
    await _auth.signInWithEmailAndPassword(email: email, password: password);
  }

  Future<void> registrarUsuari(String email, String password) async {
    await _auth.createUserWithEmailAndPassword(email: email, password: password);
  }

  Future<void> tancarSessio() async {
    await _auth.signOut();
  }
}
🛡️ Regles de Seguretat a Firestore (Security Rules):

Com que Flutter es connecta directament a Firestore sense passar per un servidor intermedi, la seguretat s'aplica al núvol mitjançant les Security Rules. Aquesta regla garanteix que cada usuari només pugui llegir i modificar les seves pròpies notes:

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /notes/{notaId} {
      allow read, update, delete: if request.auth != null && request.auth.uid == resource.data.userId;
      allow create: if request.auth != null && request.auth.uid == request.resource.data.userId;
    }
  }
}

6. Arquitectura Offline-First i Guia de Decisió

En dispositius mòbils la connexió a Internet és inestable (túnels, modes avió, cobertura feble). Una aplicació professional aplica el principi Offline-First: la interfície sempre llegeix les dades des de l'emmagatzematge local (instantani) i un repositori s'encarrega de sincronitzar els canvis amb el servidor quan hi ha xarxa disponible.

💡 Avantatge de Cloud Firestore en aquest aspecte:

Firestore inclou persistència offline activada per defecte a Android i iOS. Si l'usuari crea o modifica un document sense cobertura, Firestore l'aplica immediatament a la memòria cau local (actualitzant la UI a l'instant) i l'envia automàticament al núvol en recuperar la connexió.
